# Развёртывание V2 на отдельном VPS

Пакет рассчитан на **новый отдельный Ubuntu 24.04 LTS VPS**. Предлагаемый адрес — `app.migrantmost.ru`; сначала необходимо подтвердить владение адресом и настроить его DNS на новый IP. Эта инструкция сама не создаёт сервер и не меняет основной сайт или V1.

Схема: Nginx принимает HTTPS, отдаёт V2 по `/app/` и проксирует Django в Gunicorn `127.0.0.1:8001`. PostgreSQL слушает localhost. Секреты находятся в `/etc/most-support-v2/`, база — в стандартном закрытом каталоге PostgreSQL. Публичная папка содержит только результат `tools/build-static.py`; backend и база в неё не копируются.

## 1. Подготовить новый сервер

На новом VPS открыть 80/443 и ограничить доступ к SSH доверенными адресами средствами REG.Cloud. Не открывать наружу 5432 и 8001. Скрипты не меняют SSH, ключи, пароль root и существующий firewall.

Загрузить проверенную версию репозитория в `/opt/most-support-app-v2`. Проверить SHA коммита перед запуском. Если используется Git:

```sh
umask 022
git clone https://github.com/vsvld778/most-support-app-v2.git /opt/most-support-app-v2
cd /opt/most-support-app-v2
git log -1 --oneline
bash deploy/install.sh app.migrantmost.ru
```

Запускать от root только на новом выделенном для V2 сервере. Установщик ставит системные пакеты, создаёт отдельного пользователя `mostv2`, роль/базу `most_v2`, случайные секреты без вывода в терминал, запускает миграции, службу приложения и резервное копирование. Существующие секреты или одноимённую БД он не перезаписывает. Если установка прервётся, сначала изучить ошибку; не удалять существующую БД для повторного запуска.

На этом этапе HTTP отвечает 503, кроме проверки сертификата. Авторизация и API через открытый HTTP не обслуживаются. Регистрация остаётся **closed**, приём обращений — **disabled**.

## 2. Включить HTTPS после DNS

Проверить A/AAAA-записи: все опубликованные адреса должны вести на этот VPS. Следующая команда оператора запускается отдельно, после проверки домена; она может запросить email и принятие условий центра сертификации. Установщик не принимает условия автоматически.

```sh
certbot certonly --webroot -w /var/lib/letsencrypt \
  --cert-name app.migrantmost.ru -d app.migrantmost.ru
bash /opt/most-support-app-v2/deploy/enable-https.sh
certbot renew --dry-run
```

`enable-https.sh` проверяет наличие сертификата, тестирует Nginx перед перезагрузкой, включает таймер продления и устанавливает hook безопасной перезагрузки Nginx. При ошибке синтаксиса возвращается предыдущая конфигурация. Установленный по умолчанию сайт Nginx не удаляется.

## 3. Подготовить вход

```sh
bash /opt/most-support-app-v2/deploy/manage.sh createsuperuser
```

Пароль вводится оператором интерактивно, не передаётся в командной строке и не хранится в Git. Для сотрудников с ограниченными правами есть отдельная команда `bootstrap_coordinator`.

Проверить `https://app.migrantmost.ru/health/`, `/app/`, `/login/`, `/admin/` и `/api/v2/session/`. Гостевой ответ API — `authenticated:false`, после входа — данные текущего аккаунта. Проверить изоляцию двух тестовых пользователей и повторный вход. Публичная GitHub Pages версия продолжает работать независимо.

Nginx отдаёт серверный `/app/runtime-config.js` со значением `window.MOST_SERVER_CONFIG={enabled:true,apiBase:'/api/v2'}`. В исходниках для GitHub Pages остаётся выключенный конфиг. Он содержит только публичные параметры, никаких ключей. Двоичные вложения пока хранятся в браузере: загрузка на сервер, S3, почта и push не включаются самим развёртыванием.

Открытие регистрации и реальный приём — отдельное решение оператора. До него сохраняются `REGISTRATION_MODE=closed` и `PORTAL_INTAKE_MODE=disabled`. Для закрытого теста можно настроить приглашение и режим `test` согласно [`backend/README.md`](backend/README.md). Не менять режим на `live` без реального оператора, политики и готовой команды.

## Резервные копии и обновления

`most-support-v2-backup.timer` создаёт ежедневно SQL-дамп PostgreSQL, сжимает, проверяет gzip и хранит 14 суток в `/var/backups/most-support-v2/`. Удаляются только файлы точного формата `most-v2-db-YYYYMMDDTHHMMSSZ.sql.gz` в этой папке. Пароль БД читается из root-only pgpass. Копии содержат личные данные и должны оставаться закрытыми.

**Копия на том же VPS не защищает от потери сервера.** Перед настоящим приёмом настроить перенос зашифрованных копий во внешнее закрытое хранилище, резервирование `/etc/most-support-v2/` и тест восстановления в отдельную БД. Снимок VPS не заменяет проверку восстановления PostgreSQL. Не восстанавливать дамп поверх рабочей БД без отдельного решения оператора.

После загрузки проверенной новой версии в тот же каталог:

```sh
bash /opt/most-support-app-v2/deploy/update.sh
systemctl status most-support-v2 --no-pager
journalctl -u most-support-v2 -n 80 --no-pager
systemctl list-timers most-support-v2-backup.timer certbot.timer
```

Обновление делает дамп до миграций, обновляет зависимости и статику, затем перезапускает приложение. Для несовместимых миграций нужен заранее согласованный период обслуживания и план отката; скрипт не выполняет автоматический откат базы. Изменения Nginx/systemd отдельно проверяются и устанавливаются оператором.

## Проверка пакета

Локально проверяется синтаксис shell-скриптов. Полная проверка `nginx -t`, systemd и Django выполняется установщиком на Ubuntu; без Linux/VPS она не считается пройденной. Здоровье приложения проверяется через `/health/` после HTTPS. Источники: [Django deployment checklist](https://docs.djangoproject.com/en/5.2/howto/deployment/checklist/), [Certbot webroot и renewal](https://eff-certbot.readthedocs.io/en/stable/using.html).

## Объединённая платформа

Кабинеты открываются через `/cabinet/`. Личное пространство V2 остаётся на
`/app/`, организационное работает на `/partners/`. Оба используют одну
сессию Django на домене приложения. Условие доступа к организации — её
подтверждение и активное членство.

Миграции `0002_userworkspace_workspaceevent` и `0002_organization_workspace`
сохранены. `0003_merge_workspaces` соединяет граф. В существующей базе V2
миграция добавляет организационные таблицы, сохраняя идентификаторы аккаунтов
и личных записей. Она не импортирует данные из базы сайта. Перед переключением
сайта проверьте количество аккаунтов, членств, заявок и рабочих пространств
в обеих базах. При наличии записей в базе сайта сначала согласуйте перенос
на копии с явной таблицей соответствия идентификаторов. Совпадение внешнего
адреса почты само по себе не подтверждает владельца.

На тестовой копии проверьте один вход, переключение кабинетов, отзыв
членства, сохранение личных записей и работу двух организаций. После
миграции используйте `/admin/` → «Настройки модулей» для выбора режима и
аудитории пилота. Базовый набор даёт план, сроки, черновики, справочную
помощь и проекты. Приём заявок дополнительно зависит от
`PORTAL_INTAKE_MODE`. «Приостановить новые заявки» сохраняет переписку
по открытым, «Только просмотр» останавливает и отправку новых сообщений.

В разделе «Содержимое сайта и кабинетов» сохраните черновик объявления,
затем выберите в списке действие публикации. Содержимое на сайте передаётся
через `/api/public/site-publication/`. После проверки обеих страниц и входа
сайт может забрать опубликованный выпуск командой
`/usr/local/sbin/safspp-prepare-public --platform` на сервере сайта.
Команда обновляет ссылки и объявление после успешного чтения выпуска,
при недоступности платформы остаётся прежняя страница.
