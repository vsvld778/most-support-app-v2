# Серверная часть «Мост поддержки V2»

Исходники отдельного серверного приложения на Django 5.2 LTS. GitHub Pages запускает только интерфейс V2: этот Python-сервер **не развёрнут и не подключён к публичной V2 автоматически**. Его публикация требует отдельного сервера, базы PostgreSQL, HTTPS, настройки оператора и сотрудников фонда.

## Реализовано в коде

- Настоящие аккаунты с email и паролем, регистрация по приглашению или закрытая регистрация.
- Личный кабинет с обращениями, номером, состоянием, следующим шагом и перепиской.
- Рабочая очередь координатора в Django admin; отдельный кабинет организации.
- Организация получает только выделенное ей описание задачи и отдельный диалог. Для доступа необходимы проверенная организация, активное членство и зафиксированное согласие. Смена организации отзывает прежний доступ.
- Сессии HTTP-only, CSRF, Argon2, ограничение попыток входа и запросов, аудит и исключение приватных ответов из кеширования.
- API личного рабочего пространства V2 с изоляцией пользователей и проверкой версии, предотвращающей незаметное перезаписывание изменений с другого устройства.

В серверной части нет отправки email/SMS/push, подтверждения email, восстановления пароля, серверной загрузки файлов, автоматического юридического заключения, госинтеграций или готовых партнёрских записей. Вложения публичного интерфейса остаются в браузере. Статус обращения меняет реальный сотрудник; шаблоны не подменяют его ответ.

## Локальный запуск

Нужен Python 3.10+ (рекомендуется 3.12).

```sh
python3 -m venv .venv
.venv/bin/pip install -r requirements.txt
.venv/bin/python manage.py test --settings=config.test_settings
.venv/bin/python manage.py makemigrations --check --dry-run --settings=config.test_settings
```

Для локального сервера задайте через окружение случайный `DJANGO_SECRET_KEY` длиной минимум 50 символов, `DJANGO_DEBUG=true`, `DJANGO_SECURE_SSL_REDIRECT=false`, `DJANGO_SECURE_COOKIES=false`, `DJANGO_ALLOWED_HOSTS=localhost,127.0.0.1`. Эти отключения допустимы только локально. После `manage.py migrate` создайте администратора интерактивной командой `manage.py createsuperuser` и запустите `manage.py runserver`. Не сохраняйте рабочие ключи и пароли в Git.

## Отдельное развёртывание

1. Создать отдельную PostgreSQL и задать `POSTGRES_DB`, `POSTGRES_USER`, `POSTGRES_PASSWORD`, `POSTGRES_HOST`, `POSTGRES_PORT` в защищённом окружении процесса.
2. Задать секретный ключ, разрешённый домен, `PUBLIC_SITE_URL` и параметры HTTPS. Gunicorn запускается только на loopback; обратный прокси обязан перезаписывать forwarded-заголовки до включения `DJANGO_TRUST_PROXY=true`.
3. Выполнить `manage.py migrate`, `manage.py collectstatic --noinput`, `manage.py check --deploy`; настроить резервные копии и восстановление PostgreSQL.
4. Создать администратора, затем ограниченного координатора командой `manage.py bootstrap_coordinator --email ... --name ...`; пароль вводится скрыто интерактивно.
5. По умолчанию `REGISTRATION_MODE=closed` и `PORTAL_INTAKE_MODE=disabled`. Для пилота выбрать `REGISTRATION_MODE=invite`, передать SHA-256 приглашения через `REGISTRATION_INVITE_SHA256` и `PORTAL_INTAKE_MODE=test`. Тестовый режим явно помечает записи и требует вымышленные данные.
6. Для настоящего приёма сначала подготовить команду и документы оператора. Режим `live` требует `PORTAL_OPERATOR_NAME`, `PORTAL_POLICY_VERSION`, `PORTAL_POLICY_URL`. Наличие значений не подтверждает готовность службы помощи.

Статику V2 и серверные API при интеграции следует разместить на **одном origin**: например, приложение `/app/`, серверные маршруты `/api/v2/`, `/login/`, `/cases/`. Копирование фронтенда само по себе не включает синхронизацию. CORS не открыт, передавать cookie между GitHub Pages и отдельным сервером не предлагается. Действующее приложение V1 не меняется.

## API для последующего подключения фронтенда

`GET /api/v2/session/` возвращает `{authenticated:false,login_url}` либо `{authenticated:true,display_name,csrf_token,workspace_max_bytes}`. Вход выполняется стандартной формой `/login/`; токен CSRF хранить только в памяти страницы.

`GET /api/v2/workspace/` требует сессию и возвращает `{revision,data,updated_at}`. Новое пространство имеет `revision:0,data:{}`.

`PUT /api/v2/workspace/` требует сессию, заголовок `Content-Type: application/json` и `X-CSRFToken`. Тело: `{"revision":0,"data":{"profile":{},"modules":{}}}`. Успех возвращает следующую `revision`. При `409 revision_conflict` нужно загрузить изменения и предложить пользователю разрешить конфликт, а не перезаписывать автоматически. Предел — 48 KiB на запрос, глубина JSON 24, строки до 16000 символов; бинарные вложения в это API не включаются. Частота записи ограничена 60 запросами за 10 минут на пользователя.

Рабочее пространство — личные черновики. Оно не даёт прав координатора, не назначает партнёров и не отправляет обращения. Реальное обращение создаётся отдельной серверной формой `/cases/new/`, где проверяются режим приёма и согласие.

## Проверки

Сохранены тесты исходного портала на границы доступа, отзыв доступа, передачу другой организации, CSRF/XSS, приглашения и ограничение запросов. Добавлены проверки API на изоляцию пользователей, конфликт версий, обязательный CSRF, запрет чужого origin, пределы JSON и попытку подмены владельца. Тестовые настройки используют отдельную БД в памяти и не подключаются к рабочим данным.
